# AGENTS.md — read this first

You are an AI coding agent (Claude Code, Codex, Antigravity, etc.) working on this repo,
possibly on a different machine than the agent that last touched it. This file tells you what
the project is, the rules you must follow, and how the two devices coordinate through GitHub.

## What this project is
An AI **dating-profile coach** for the Indian market. It (1) **standardizes the user's own
profile** — scores it, rewrites the bio, ranks photos — and (2) **drafts messages** to matches.
It can read a live Tinder account via a connector. Full detail: [README.md](README.md).

## Non-negotiable rules (do not "improve" these away)
1. **The AI never sends messages.** It only *drafts*; the human reviews and sends. `send_message()`
   in `src/connector.py` is a manual-only escape hatch. Never call it from the brain, a loop, or a demo.
2. **Reading is automated; sending is not.** Don't build auto-swipe / auto-reply / bulk messaging.
   It deceives third parties and gets accounts banned. This is a product decision, not a TODO.
3. **No secrets in git.** `.env` is gitignored and holds the HF token + Tinder token. Never commit
   it, never paste a real token into `.env.example`, code, tests, or commit messages.
4. **No AI attribution in commits.** No `Co-Authored-By`, no "generated by" lines.
5. **Keep the contract stable.** The brain talks to the world only through the `Profile`/`Match`
   objects in `src/schema.py`. Change those carefully — connector and brain both depend on them.

## Architecture (3 swappable layers)
```
CONNECTOR  src/connector.py        -> clean Profile/Match (src/schema.py)
  (Tinder via vendored tinder.py)        |
LLM BACKEND src/llm.py  (HF or Ollama)   v
BRAIN      src/coach.py + knowledge/dating_profile_kb.md
  standardize_profile() / draft_replies() -> structured Pydantic output
```
- **LLM is pluggable** via `LLM_BACKEND` env: `hf` (Hugging Face API, needs `HUGGINGFACEHUB_API_TOKEN`)
  or `ollama` (local). No Anthropic/Claude API — do not add it.
- **HF gotcha:** instruct models are served as `task="conversational"` (chat), not `text-generation`.
- The knowledge pack (`knowledge/dating_profile_kb.md`) is the tunable rubric — edit it to change
  behavior; no code change needed.

## Setup (fresh clone)
```bash
python -m venv .venv
# Windows:  .\.venv\Scripts\Activate.ps1   |  macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # fill LLM_BACKEND + the matching token/model
```

## Run
- Offline demo (mock data): `python src/demo.py`
- Live (your machine, real token): `python src/connect_demo.py` — see README "token guide".
  **Run live only on a personal/home network**; cloud IPs get the account blocked.

## Before you push — ALWAYS
```bash
pytest -q          # must pass; CI runs the same thing
```
Tests are offline (no network, no keys). If you add a feature, add/extend a test in `tests/`.

## How the two devices coordinate (this is the "communication channel")
GitHub is the shared brain. Workflow every session:
1. `git pull` first.
2. Read the latest entry in [HANDOFF.md](HANDOFF.md) — that's what the other agent/device did last
   and what it wants done next.
3. Do the work. Run `pytest -q`.
4. **Append a new entry to HANDOFF.md** (date, device/agent, what changed, what's next, anything
   blocked). This is how you talk to the agent on the other device.
5. Commit (clear message, no AI attribution) and push.
6. **CI is the ack:** a green check on the pushed commit means the other side can safely pull.
   A red check is a message too — fix it or note it in HANDOFF.md before handing off.

Keep changes small and the contract (`schema.py`) stable so both sides stay in sync.
